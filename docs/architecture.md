# Архитектура

## Три цели CMake

Проект собирается в три цели. Деление не формальное: оно определяет, что можно
проверить тестом, а что нельзя.

| Цель | Что это | Из чего собирается |
|---|---|---|
| `PacmanLib` | статическая библиотека с логикой игры | `Config.cpp`, `Config.h`; линкует `nlohmann_json` |
| `Pacman` | исполняемый файл игры | `main.cpp`; линкует `PacmanLib` |
| `PacmanTestRunner` | тесты | `Tests/ConfigTest.cpp`; линкует `PacmanLib` и `GTest::gtest_main` |

Из теста можно вызвать функцию библиотеки, а `main` — нельзя: у исполняемого
файла нет интерфейса, к которому мог бы обратиться другой код. Поэтому вся
логика, которую нужно проверять, живёт в `PacmanLib`, а `main.cpp` остаётся
тонким: открыть файл, вызвать функцию библиотеки, напечатать результат,
перехватить исключение и вернуть код выхода.

Описание целей — `src/Pacman/CMakeLists.txt`; корневой `CMakeLists.txt`
задаёт стандарт C++23, находит зависимости через `find_package`, включает
модули и подключает подпроект. Бинарные файлы всех целей складываются в один
каталог `build/bin/<Config>/`.

Зависимости приходят от Conan: `nlohmann_json` для разбора JSON, `gtest` для
тестов — список в `conanfile.txt`, профили сборки в `profiles/`.

## Конфигурация из данных

Настройки окна не зашиты в код, а читаются из `config.json`:

```json
{
  "title": "Pac-Man",
  "window": { "width": 800, "height": 600 }
}
```

Разбором занимается `LifeExe::parseConfig` — см.
[справочник API](api/index.html). Ключевое решение в её подписи: функция
принимает `std::istream&`, а не путь к файлу.

```cpp
GameConfig parseConfig(std::istream& input);
```

Открытие файла — работа вызывающего кода, а разбор — работа библиотеки. Игра
передаёт `std::ifstream`, тест передаёт `std::istringstream` с нужным
документом прямо в теле теста: не нужны файлы-заготовки на диске, временные
каталоги и уборка после теста. Проверить поведение на битом JSON или на
отсутствующем ключе становится тремя строками.

Ошибки разбора сообщаются исключением `std::runtime_error`, и сообщение
называет ключ, которого не хватает: человек, запустивший игру, должен понять
из сообщения, что именно править в `config.json`.

## Модули CMake

Настройки, которые применяются ко всем целям, вынесены в `cmake/` — каждая
своим модулем с функцией. Так правило описано один раз, а не скопировано в
каждую цель.

| Модуль | Что даёт |
|---|---|
| `cmake/CompilerWarnings.cmake` | `set_project_warnings(<target>)` — `/W4 /WX /permissive-` для MSVC, `-Wall -Wextra -Wpedantic -Werror` для GCC и Clang |
| `cmake/Sanitizers.cmake` | опция `ENABLE_ASAN` (по умолчанию `OFF`) и `enable_sanitizers(<target>)` — инструментирование AddressSanitizer |
| `cmake/ClangFormat.cmake` | цели `format` и `format-check`; ищет `clang-format` в PATH и в каталогах установленной Visual Studio |

Все три функции применяются к каждой из трёх целей. Предупреждение
компилятора считается ошибкой: компилятор нашёл вероятную ошибку, но не
уверен в ней, — с `/WX` такую находку нельзя проигнорировать и нельзя
накопить.

`Sanitizers.cmake` на MSVC делает больше, чем добавляет флаг: вырезает `/RTC1`
(несовместим с ASan), выключает инкрементальную линковку, отключает разметку
контейнеров STL (`_DISABLE_STL_ANNOTATION`) — gtest из Conan собран без неё,
иначе линковщик выдаёт `LNK2038` — и копирует `clang_rt.asan_dynamic-x86_64.dll`
рядом с исполняемым файлом: runtime лежит у компилятора и в PATH его нет.
