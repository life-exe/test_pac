# Разработка

## Скрипты `automation/`

Любая команда, которую нужно помнить дольше одного раза, становится скриптом.
Скрипты запускаются из любого каталога: пути вычисляются от файла
`automation/common.py`, а не от текущего каталога.

| Скрипт | Что делает |
|---|---|
| `generate_project_files.py` | устанавливает зависимости Conan для Debug и Release и конфигурирует проект CMake |
| `build_debug.py` | собирает конфигурацию Debug |
| `build_release.py` | собирает конфигурацию Release |
| `run_tests.py` | собирает Debug и прогоняет тесты через CTest, пишет отчёт JUnit в `build/test-report.xml` |
| `run_coverage.py` | измеряет покрытие под OpenCppCoverage; с `--min N` возвращает код 1 ниже порога |
| `run_asan.py` | собирает `build-asan` с `ENABLE_ASAN=ON` и прогоняет тесты под AddressSanitizer |
| `format_files.py` | форматирует исходники; с `--check` только проверяет |
| `run_tidy.py` | прогоняет статический анализ clang-tidy |
| `build_docs.py` | собирает справочник API и сайт документации |
| `clean.py` | удаляет артефакты сборки; с `--dry-run` только показывает, что будет удалено |

## Перед коммитом

Порядок такой: сначала то, что падает быстро, потом длинное.

```powershell
python automation/format_files.py --check
python automation/run_tests.py
python automation/run_tidy.py
python automation/run_coverage.py --min 70
python automation/run_asan.py
python automation/build_docs.py
```

Тот же набор выполняет CI на чистой машине `windows-latest`, поэтому локальный
прогон — способ не ждать красного прогона после push. Файлы в коммит
добавляются по имени: `git add <файл>`, чтобы в коммит не попало лишнее.

## Покрытие

Покрытие измеряет [OpenCppCoverage](https://github.com/OpenCppCoverage/OpenCppCoverage):
он запускает тесты под отладчиком и по `.pdb` сопоставляет выполненные
инструкции со строками исходников — пересборка с особыми флагами не нужна.
Отчёты пишутся в `build/coverage/`: `html/index.html` для чтения человеком,
`coverage.xml` в формате Cobertura для CI.

Измеряется только Debug: в Release оптимизатор переставляет и выбрасывает
строки, и отчёт по нему вводит в заблуждение.

Порог в CI — 70%, он держится с запасом ниже текущего покрытия. Его задача не
в том, чтобы поднять число, а в том, чтобы покрытие не упало незаметно, когда
в проект добавят непроверенный код.

## Статический анализ

Поверх предупреждений компилятора работает
[clang-tidy](https://clang.llvm.org/extra/clang-tidy/). Он идёт в составе
Visual Studio и запускается через code analysis MSBuild, поэтому база
компиляции (`compile_commands.json`) не нужна: флаги каждого файла MSBuild
передаёт сам.

Обычная сборка clang-tidy не запускает — полный прогон занимает 15–20 секунд,
и платить эти секунды при каждой сборке незачем; анализ вынесен в отдельную
команду `run_tidy.py`.

Правила заданы файлом `.clang-tidy`: включены семейства `bugprone-*`,
`performance-*`, `modernize-*`, `readability-*` и `misc-const-correctness`,
отдельные вкусовые проверки выключены минусом. `WarningsAsErrors: '*'` делает
любую находку ошибкой, поэтому анализ либо проходит целиком, либо падает —
предупреждения не накапливаются. `HeaderFilterRegex` ограничивает сообщения
нашими исходниками: находки в заголовках `nlohmann_json` и gtest не
показываются.

## AddressSanitizer

[AddressSanitizer](https://learn.microsoft.com/cpp/sanitizers/asan) находит
ошибки работы с памятью во время выполнения: выход за границу блока, обращение
к освобождённой памяти, двойное освобождение — то, что не видно ни
компилятору, ни clang-tidy, потому что зависит от данных. Компилятор вставляет
проверку вокруг каждого чтения и записи и ставит запретные зоны вокруг
выделенных блоков, поэтому ошибка останавливает программу в момент обращения и
с отчётом: тип ошибки, адрес, строка обращения и строка, где блок выделен.

Нужен компонент **C++ AddressSanitizer** из Visual Studio Installer.

Сборка отдельная: инструментированные объектные файлы несовместимы с
обычными, а сама сборка медленнее в два-три раза. Поэтому `build-asan/`
живёт рядом с `build/` и не мешает обычной работе; toolchain от Conan
переиспользуется из `build/`.

В CI тесты под санитайзером идут сразу после сборки Debug, до обычных тестов:
ошибка работы с памятью в обычной сборке Debug открывает модальное окно
отладочной кучи MSVC, нажать в нём на раннере некому, и шаг висит до таймаута
CTest. Под ASan прогон падает сразу и с отчётом, а шаги после упавшего в
GitHub Actions пропускаются.

## Документация

Документация лежит в репозитории рядом с кодом, меняется тем же коммитом,
собирается скриптом и проверяется в CI.

- **Справочник API** — комментарии `///` в заголовках `src/Pacman/*.h`,
  собирает Doxygen по настройкам из `Doxyfile`. Недокументированная публичная
  сущность — ошибка сборки (`WARN_AS_ERROR`), поэтому справочник не отстаёт
  от кода. Результат — `docs/api/`, каталог сгенерированный и в `.gitignore`.
- **Страницы о проекте** — Markdown в `docs/`, собирает MkDocs по описанию в
  `mkdocs.yml`. Битая ссылка — ошибка сборки (`--strict`). Версии MkDocs и
  темы закреплены в `requirements-docs.txt`, чтобы сайт собирался одинаково
  локально и в CI.

Собрать всё одной командой:

```powershell
python automation/build_docs.py
python automation/build_docs.py --serve   # предпросмотр на http://127.0.0.1:8000
```

Doxygen всегда идёт первым: без каталога `docs/api` строгий MkDocs упадёт на
ссылке из навигации. Готовый сайт — в `build/docs/site`.
