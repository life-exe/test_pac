# Подготовка коммита                                                                                                                                      
                                                                                                                                                          
## Порядок действий                                                                                                                                       
                                                                                                                                                          
1. Выполнить `git status --short` и `git diff --staged` (если индекс пуст — `git diff`).                                                                  
2. Проверить изменения на частые оплошности:                                                                                                              
    - не попали ли в список временные файлы, логи (`LastCoverageResults.log`) или артефакты сборки;                                                        
    - не остались ли забытые отладочные принты (`std::cout`, `printf`);                                                                                    
    - не ослабляются ли существующие тесты или правила `.clang-tidy`.                                                                                      
3. Определить уровень риска изменений (`Tier: Low`, `Tier: Standard` или `Tier: High`). Если в одном диффе смешаны изменения разных уровней или           
несвязанные задачи — предложить разбить их на отдельные атомарные коммиты с точными командами `git add <файлы>`.                                          
4. Составить сообщение коммита для людей:                                                                                                                 
    - заголовок `<type>(<scope>): <summary>` (`feat`, `fix`, `docs`, `build`, `ci`, `refactor`, `test`, до 72 символов);                                   
    - краткое тело: что изменилось и **почему** (мотивация решения);                                                                                       
    - секция `Testing:` со списком конкретных тестов или проверок, подтверждающих изменение (либо `- none, docs only`);                                    
    - футер `Tier: <Low | Standard | High>` (и `AI-Review: +1`, если перед этим был пройден локальный `/code-review`).                                     
5. **Ограничение:** никогда не выполнять `git commit` или `git push` самостоятельно — только вывести готовые команды для разработчика.
