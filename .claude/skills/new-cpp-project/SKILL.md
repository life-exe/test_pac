# Новый проект C++ по спецификации

Аргумент — имя проекта в PascalCase (например, `Tetris`). Второй аргумент,
необязательный, — каталог назначения; по умолчанию `../<имя в нижнем регистре>`.

## Порядок

1. Прочитать `SCAFFOLD.md` целиком. Это техническое задание; отступать от
   него нельзя, дополнять своими решениями — тоже. Если для какого-то файла
   или настройки спецификация не даёт ответа, остановиться и задать вопрос:
   ответ должен попасть в спецификацию, а не остаться в этой сессии. Файлы
   этого репозитория образцом не считать: скилл должен давать один и тот же
   результат из любого каталога.
2. Убедиться, что каталог назначения пуст или не существует. Иначе
   остановиться и спросить.
3. Создать все файлы из раздела «Структура» с подстановкой `<Name>`:
   каталог `src/<Name>`, `project(<Name>)`, `HeaderFilterRegex`, `PROJECT_NAME`
   в Doxyfile, `site_name`, заголовок README, `title` в `config.json`,
   приветствие в `main.cpp` и ожидания в тестах.
4. Проверить результат самостоятельно, из каталога проекта, в этом порядке,
   останавливаясь на первой ошибке и исправляя файлы:
   `python automation/generate_project_files.py`, `python automation/build_debug.py`,
   `python automation/run_tests.py`, `python automation/format_files.py --check`,
   `python automation/run_tidy.py`, `python automation/run_asan.py`,
   `python automation/build_docs.py`.
5. Инициализировать git (`git init`, один коммит `chore: project scaffold`),
   ничего не публиковать.
6. Сообщить пользователю: путь, список созданных файлов по разделам
   спецификации, вывод последней команды каждого шага проверки одной строкой,
   и команду приёмки: `python <курс>/checks/scaffold.py <каталог>`.

## Правила

- Имена целей и путей — только производные от `<Name>`; никаких `Pacman`,
  `App`, `Game` в сгенерированном проекте, кроме случаев, когда так называется
  сам проект.
- Версии инструментов и библиотек — из спецификации, не новее и не старее.
- Комментарии в коде, CMake и скриптах — на английском, короткие, объясняют
  причину, а не действие.
- Не добавлять файлы, которых нет в спецификации: ни лицензии, ни
  `CONTRIBUTING.md`, ни примеров, ни второго конфигурационного файла.
- Если какой-то шаг проверки не проходит и причина в спецификации, а не в
  сгенерированном файле, остановиться и сообщить: спецификацию правит человек.
- Единственный источник содержимого — `SCAFFOLD.md`. Не читать другие файлы
  репозитория ради «как тут принято»: пробел в спецификации — повод для
  вопроса, а не для подражания.
